# 多用户机器上的目录映射：清单、权限与盘符冲突

> 利益披露：作者所在团队维护文末提到的 ScsSubst，与该产品存在利益关系。以下为实测记录，仅代表我的环境。

把文件夹映射成盘符，在个人机器上一条命令就完事；到了多人共用的机器上，会冒出一堆个人机器上根本看不到的问题。

## 一、映射必须落在每个用户自己的会话里

目录到盘符的映射是用户会话级的：A 用户建的盘符，在 B 用户登录后不存在，除非登录时各自重建。

这就是"我这边好好的，你那边报盘符已存在"的根源——同一个字母，两台机器的映射目标还不一样。

**结论**：映射清单要能导出、能导入，换机器时按清单重建。

## 二、盘符冲突是常态，不是意外

同事机器上 C 到 Z 大半被光驱、虚拟磁盘、加密分区占着。你想用 Q 盘，结果 Q 已经被别的映射或卷占了。

**结论**：给团队定一段盘符区间（例如 R 到 U），并在清单里写死。

## 三、权限要跟着目录走

映射本身不改变 ACL，但映射后的路径不同，某些只按路径白名单放行的脚本会突然不认。

**结论**：排查问题时，把映射路径还原成真实路径再测一次。

## 四、目标目录被删除后的残留

映射还在，目标目录没了，于是出现"盘符在、点进去是空的"。删除目录后不同步清理映射，是最常见的脏状态。

**结论**：定期对一次清单，把失效项清掉。

## 五、开机重建的顺序问题

开机自启脚本如果早于网络盘或磁盘策略就绪，映射会失败。稳妥做法是延迟几秒重试若干次，而不是跑一次就算。

**结论**：重建逻辑要带重试。

## 六、路径长度是共享的痛点

把深层目录映射成短盘符，本来就是为路径过长准备的；但如果映射目标本身也很深，收益就有限。

**结论**：优先映射那些本身路径就长的目录。
